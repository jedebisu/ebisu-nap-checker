# G-MAPS — Sales Demo App for Globe Telecom

Date: 2026-11-13
Status: Draft (pending builder check + owner approval)

## Intent and Why

The owner (EBISU Document Process Services) wants to sell the NAP Checking
capability of the EBISU T&A app to Globe Telecom as a standalone product.
To pitch it, a separate branded demo app — **G-MAPS** — will be shown to
Globe, running for a team outside EBISU's employment. The demo must look
like a Globe product, not a re-skinned EBISU app, and must **not** expose
EBISU's production backend, employee accounts, or attendance data.

## Goals

- A installable Android APK named **G-MAPS**, fully rebranded (Globe-style
  blue palette, new icon, zero EBISU branding anywhere visible).
- Core features only: **Login** (with **Create Account**), and
  **NAP Checking** (the interactive map).
- Account self-service for Globe evaluators: register with an **invitation
  key**, verify an **OTP emailed to them**, receive a temporary password,
  and set their own password on first login.
- A **separate demo backend** (copy of the existing API) with its own
  database, holding **real NAP facility data** copied from production, and
  seeded demo accounts the owner hands to Globe evaluators.
- An **owner-only admin console web page** for generating invite codes
  (with a chosen use count) and resetting OTP-locked accounts.
- EBISU production (Render `selfie-api-sqgh`, Supabase prod DB) untouched.

## Non-goals

- No attendance/clock-in, camera selfies, history/calendar, leave requests,
  profile screens, or background location tracking.
- No writes from the demo app to the production database.
- No EBISU branding, package id, or signing key reuse.
- No iOS build in this phase (Android APK only).

## Anti-goals (what would make this a failure)

- Globe evaluators landing in EBISU's production system or seeing employee
  attendance data.
- The demo failing during the pitch because it depends on the production
  server (deploys, rate limits, shared load).
- Any leftover "EBISU" string visible in the UI or app listing.
- Demo evaluators registering without a valid invitation key, or an
  invitation key being reusable forever (keys must enforce their use
  count).

## Constraints

- The EBISU T&A APK cannot be edited directly (compiled Hermes bytecode);
  the app is rebuilt from source.
- Source of truth for the app: `selfie-attendance/mobile/` (Expo / React
  Native, bare workflow with `android/` folder, `build-apk.sh` flow).
- Source of truth for the API: `selfie-attendance/server/` (Node/Express,
  deployed on Render free tier, Supabase Postgres).
- Build environment already proven on this Mac: Android SDK at
  `~/Library/Android/sdk`, Java 17 (`/opt/homebrew/opt/openjdk@17`),
  `npx expo prebuild -p android` + `./gradlew assembleRelease`.
- NAP data ownership: NAP Facility Summary Reports originate from Globe,
  so presenting that data back to Globe is acceptable to the owner.

## Approaches Considered

**Backend data source** (owner decision made):
1. *Separate demo backend with real NAP data* — **CHOSEN.** Real-feeling
   demo, zero production risk, resettable. Costs one Render service +
   one Supabase project.
2. Same production API with limited demo accounts — rejected: demo
   logins would live in the real user table and Globe would be inside
   the live system.
3. Baked-in static data, no server — rejected: login that doesn't really
   authenticate undercuts a sales demo.

**App production method**: rebuild from the existing Expo source
(effectively the only viable way — APK bytecode can't be feature-stripped).

## The Design

### 2. Mobile app (`app/`)

Copy `selfie-attendance/mobile` (excluding `node_modules`, `android/`,
build outputs; `android/` is regenerated by `expo prebuild`).

Stripping:
- Screens kept: `LoginScreen`, `NapMapScreen`. Deleted: `HomeScreen`,
  `CameraScreen`, `HistoryScreen`, `LeaveApprovalScreen`,
  `LeaveRequestScreen`, `ProfileScreen`.
- Navigation: `AuthProvider` → if logged out, `LoginScreen`; if logged
  in, **NapMapScreen directly** (no tab bar, no stack of other screens).
- A **logout** affordance is added to the NAP map header (icon button)
  since the Profile screen that previously held it is gone.
- Services: keep `api.js`, `network.js`, `cache.js` (NAP parts), and the
  NAP-only helpers in `utils/helpers.js`. Remove `locationTracker`,
  `syncService` and any attendance/leave/queue-sync code paths.
- `AuthContext` trimmed: login/logout/token persistence only; drop the
  offline sync queue and location-tracking hooks.
- Android permissions reduced to `ACCESS_COARSE_LOCATION` +
  `ACCESS_FINE_LOCATION` (map + "near me" need location; the NAP screen
  does not need camera/background-location/foreground-service).

Auth flow (new):
- **Login = email + password.** The legacy employee ID + PIN scheme is
  dropped in G-MAPS (see Open Calls). Login screen gains a
  **"Create Account"** button.
- **Registration flow** (new screens, Globe-styled):
  1. *Create Account form:* Firstname, Lastname, Email, Mobile number,
     Invitation Key.
  2. Invitation key is validated server-side (exists, not exhausted,
     not expired). A key covers a configurable number of uses; each
     successful registration consumes one use.
  3. *OTP screen:* 6-digit OTP sent to the email via Resend (owner's
     existing Resend account + `ebisudps.com` domain). Expires after
     **5 minutes**; can be resent.
  4. *Wrong-OTP lockout:* after **6 wrong attempts** the account waits
     **5 minutes**; further wrong attempts escalate **10 min → 30 min →
     1 hour**, staying at 1 hour thereafter. Counters reset on
     successful verification. The lockout message tells the user they
     can ask the administrator to reset the account (done from the
     admin console, below).
  5. On correct OTP, the server creates the account and emails a
     **random strong temporary password** (Resend). The registration
     screen directs the user to the login screen.
  6. On first login with the temporary password, the app forces a
     **password setup** step: minimum **8 characters, at least 1
     uppercase, at least 1 special character**. After setup, normal
     email + password login applies.
- Passwords hashed server-side (bcrypt); tokens as today (JWT).

Rebranding:
- Display name: **G-MAPS** (all headers, splash, app listing).
- `app.json`: name/slug `gmaps`, Android package
  `com.gmaps.demo` (builder call, see Open Calls), version 1.0.0,
  versionCode 1. Keeps the Google Maps API key config (same key is fine
  for the demo; it's map-tile rendering only).
- Palette: Globe-style blues (primary ≈ `#00539B` family, per current
  Globe branding) replacing the EBISU tan (`#c8956c`) across login,
  map header, status badges, spinners.
- New app icon + adaptive icon + splash (G-MAPS mark on Globe blue).
- Grep sweep: no "EBISU"/"ebisu" strings remain in user-facing text.

### 3. Demo backend (`server/`)

Copy of `selfie-attendance/server` with:
- Its own **Supabase project** (free tier) — NAP tables copied from
  production via the existing export/UPSERT tooling; users table seeded
  fresh with demo accounts (owner assigns demo email addresses +
  starting passwords).
- Deployed as its own **Render web service** (free tier), same
  `render.yaml` pattern.
- **Auth reworked for the demo model:** email + password (bcrypt) login,
  JWT tokens as today. Registration endpoints:
  - `POST /api/auth/register` — validates invitation key + fields,
    issues OTP (hashed, 5-min TTL).
  - `POST /api/auth/verify-otp` — verifies OTP, enforces the escalating
    wrong-attempt lockout (5/10/30/60 min), creates the account, emails
    the temporary password, consumes one invitation-key use.
  - `POST /api/auth/login` — email + password; flags
    `must_change_password` when the temporary password is still active.
  - `POST /api/auth/setup-password` — sets the real password (8+ chars,
    1 uppercase, 1 special).
- **Invitation keys:** new table (`key`, `max_uses`, `used_count`,
  `created_by`, `created_at`, optional `expires_at`). A key covers a
  configurable number of uses; each successful registration consumes
  one.
- **Admin console (web landing page, owner-only):** served by the demo
  Express server at `/admin` — a single-page Globe-styled console,
  protected by the admin token from the environment (simple token login
  form; token never hard-coded). Two functions:
  1. *Generate invite code:* pick the number of uses, get the code +
     copyable link/text to hand to an evaluator.
  2. *Reset locked accounts:* list accounts currently in OTP lockout,
     clear the lockout/attempt counters with one click.
  No admin login lives inside the mobile app.
- **Email:** Resend API (owner's existing account, sending domain
  `ebisudps.com`); API key in Render env vars, never committed. Two
  templates: OTP email and temporary-password email.
- NAP endpoints (`/api/naps`, `/naps/nearest`, `/naps/:id`,
  `/naps/stats/summary`, `/naps/search`) are the ones the map screen
  consumes; attendance/leave endpoints removed for a smaller attack
  surface.
- CORS/origins and any push/notification integrations disabled if they
  exist.

### 4. APK build

`build-apk.sh` adapted: archives as `G-MAPS-v1.0.apk` /
`G-MAPS-latest.apk`. Same prebuild + `assembleRelease` flow, freshly
generated signing key for the new package (new keystore, stored with the
project docs, not committed).

## Open Calls (builder settles unless owner objections received)

- Package id `com.gmaps.demo` — **owner agreed.**
- Demo backend URL naming (e.g. `gmaps-api.onrender.com`).
- Single-screen header logout icon (vs. a settings sheet).
- **Login becomes email + password** — owner agreed; users register with
  their own email addresses. Seeded demo accounts therefore get demo
  email addresses (e.g. `demo1@ebisudps.com`).
- Beyond the 1-hour lockout tier, further wrong attempts keep the 1-hour
  wait (cap); the owner resets accounts from the admin console.
- Attendance/leave endpoints are removed from the demo server — this
  app is NAP Checking only. **Owner confirmed.**
- OTP and temp-password emails come from an `@ebisudps.com` address
  (exact From name is a builder nicety).
